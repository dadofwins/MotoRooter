### Found on the way, none of it asked for

- **Every chat-built trip was born paved.** Three hardcoded defaults answered "what intent does a
  new leg get" and two disagreed with the third. `Trip.default_intent` — which the integrator had
  approved months earlier, called a convenience, and dropped — now answers it once.
- **`add_waypoint` accepted model-recalled coordinates unvalidated**, 30 m out for a famous town
  and silently wrong for a forest-road junction. There is no coordinate argument any more.
- **The judge-zero, open all day, is solved**: a misplaced quote in one key made `json.loads`

- **Validation routed the whole trip on every waypoint edit**, so a failure anywhere refused an
  unrelated edit — and it routed it under the wrong intent, asking Google about dirt.
- **A round trip broke the route list**, because rows were keyed on the coordinate and coming
  home repeats one. Caused by an earlier integrator review note.
- **Nine WCAG AA contrast failures in light mode**, from 37 ad-hoc muted colours across five

## What is not obvious about each

**1 — the repeat question. Diagnosed, and it is neither a prompt nor a state defect.** The turn
was captured: his answer was in the conversation and the model had everything. It asked again
because **there is no path to action** — `find_places` needs a route, a route needs waypoints,
waypoints need coordinates, and **forward geocoding does not exist anywhere in this project**.
The prompt says never invent a place, so asking again is the only behaviour left. It was correct
inside a closed loop.

Two consequences:

- **Forward geocoding must be built.** It was assigned in a mail this morning, never tracked, and
  evaporated — the root cause of the first complaint from the first real session is an item the
  integrator assigned and lost. A mail queue is not a backlog.
- **`add_waypoint` accepts model-recalled coordinates unvalidated**, via an exemption skipping
  routing below two waypoints. Measured at 30 m for Woodinville and Leavenworth, which is what
  makes it dangerous: good recall on famous towns means nothing looks wrong, and it will be
  silently wrong for a forest-road junction. The exemption's justification — that the second
  waypoint catches a bad first one — is false, because a waypoint 50 km off routes perfectly well
  from 50 km off. This breaks the root rule that LLM-proposed geography is validated before it
  reaches the map, at the one place nothing downstream can catch.

Order matters: **geocoding first**. Closing the exemption alone turns a repeated question into a
flat refusal, which is worse. The likely shape is a tool that takes a *name* and geocodes
server-side, so inventing a coordinate becomes structurally impossible rather than prohibited by
prompt — the mouse path keeps taking coordinates because a human pointed at a map.

**4 — the chain.** `find_places` and `add_poi_to_route` both exist, so this is largely
orchestration and prompting rather than new tools. Two constraints. It is an **autonomous route
edit**, so "ranks highly enough" needs a defensible threshold and the rider needs to see what
happened and undo it. And the mouse equivalent already exists — the per-group route-through
buttons — so this does not create a chat-only capability, which is the rule that matters.

Likely needs a contract addition: discovery progress inside a chat turn. `ChatEvent` has
`tool_started` / `tool_finished` and nothing between, so a chat-initiated `find_places` is
currently a silent 30+ seconds. That is item 2's real cause on the chat path.

**6 — incremental scoring, and the tension.** Judging is deliberately **one call over the whole
batch** because the judge compares candidates against each other; subdividing damages the
ranking. So "scoring 1/41" cannot come from 41 calls.

The way out is to **stream the judge's response and count entries as they parse**. One call,
ranking intact, real increments. The OpenAI client already streams for chat.

Also note **41 candidates is far larger than anything measured** — the judge was tested at 6–11.
Road-expansion (+50–63%) and a three-day corridor together produced it. The unexplained judge-zero
was suspected to be truncation on large batches, so this is both the reason scoring is slow *and*
the most likely reproduction we have. Capture the reply if it fires.

**7 — the pane.** A second pane rather than a section in the rail. His words: *"pop out a second
right hand (or left hand if easier) pane that can be dismissed with an X in the corner."*

## Sequencing

a contract proposal).

Frontend: **3 + 5** (both small) → **7** → **2** (may wait on backend's chat progress events).

not blocked at the end.
